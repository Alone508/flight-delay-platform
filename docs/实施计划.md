# 航班延误监测与预测平台 — 全栈大数据实施计划

## Context

课程大作业要求构建一个**全栈大数据处理与展示系统**，必须覆盖五层：

1. 数据采集层（Flume / Logstash / Sqoop）
2. 数据存储层（HDFS / HBase / MySQL）
3. 数据处理层（Spark / Flink）
4. API 服务层（Spring Boot）
5. 前端展示层（Vue.js / ECharts）

团队 4 人，环境为 Ubuntu 单机伪分布式，数据量 2–5GB，必须体现 Spark SQL/DataFrame 与 MLlib。经比较四个候选方向后选定 **航班延误监测与预测平台**：撞题率最低、天气 API 提供真实的采集层故事、延误预测模型可解释性强；实时链路采用**回放器模拟数据源 + Flume 真实采集**的课程项目标准做法。

目标产出：一个可演示的端到端系统——航班事件与天气数据经 Flume 进入 Kafka/HDFS，Spark 实时计算机场延误 KPI 并写入 HBase/MySQL，Spark 离线完成延误分析与 MLlib 预测，Spring Boot 提供 REST API，Vue3 + ECharts 展示实时大屏、延误分析、预测结果与航班明细。

| 数据 | 来源 | 规模 | 用途 |
|---|---|---|---|
| 航班记录 | [Kaggle: Flight Delay and Cancellation 2019–2023](https://www.kaggle.com/datasets/patrickzel/flight-delay-and-cancellation-dataset-2019-2023) `flights_sample_3m.csv` | 300 万行，约 30 列，~1GB | 批处理、ML、回放数据源 |
| 实时天气 | [Aviation Weather Center METAR API](https://aviationweather.gov/api/data/metar?ids=KJFK,KLAX&format=json&hours=1) | 20 个机场，每小时更新 | 实时天气关联、告警 |
| 备用天气 | [Open-Meteo](https://api.open-meteo.com/v1/forecast?latitude=40.64&longitude=-73.78&current=temperature_2m,wind_speed_10m,precipitation&hourly=visibility) | 无需密钥 | AWC 不可用时降级 |
| 机场坐标 | OurAirports `airports.csv`（或 OpenFlights `airports.dat`） | 约 8 万行 | 地图可视化、天气按经纬度采集 |
| 历史天气（可选） | Open-Meteo Archive API | 20 机场 × 演示时段 | ML 特征增强 |

**下载命令**

```bash
kaggle datasets download -d patrickzel/flight-delay-and-cancellation-dataset-2019-2023 -p ~/data/raw
unzip ~/data/raw/flight-delay-and-cancellation-dataset-2019-2023.zip -d ~/data/raw/flights
```

**关键字段**（以 `df.columns` 实际输出为准）：
`FL_DATE, AIRLINE, AIRLINE_CODE, FL_NUMBER, ORIGIN, DEST, CRS_DEP_TIME, DEP_TIME, DEP_DELAY, ARR_DELAY, CANCELLED, CANCELLATION_CODE, DIVERTED, CRS_ELAPSED_TIME, AIR_TIME, DISTANCE, DELAY_DUE_CARRIER, DELAY_DUE_WEATHER, DELAY_DUE_NAS, DELAY_DUE_SECURITY, DELAY_DUE_LATE_AIRCRAFT`

**两个必须注意的数据特性**

- `DELAY_DUE_*` 五列**只在延误 ≥15 分钟时有值**，五者之和等于该航班的到达延误分钟数；用于延误原因分析，**绝不能作为预测特征**（标签泄漏）。
- 预测特征也不得使用 `DEP_TIME / DEP_DELAY / ARR_DELAY / TAXI_OUT / WHEELS_OFF / AIR_TIME` 等事后字段。

## 2. 总体架构

```
                 ┌──────────────── 采集层 ────────────────┐
Kaggle CSV ──► flight_replay.py ──► 日志文件 ──► Flume taildir ─┬─► Kafka: flight-events
                                                                 └─► HDFS /flight/ods/events
AWC/Open-Meteo ─► weather_collector.py ──► 日志文件 ──► Flume ──┬─► Kafka: weather-events
                                                                 └─► HDFS /flight/ods/weather
MySQL 维度表 ──► Sqoop import ──► HDFS /flight/dim

                 ┌──────────────── 处理层 ────────────────┐
Kafka ──► Spark Structured Streaming ──► MySQL ads_realtime_* + HDFS DWS
Kafka ──► hbase_sink.py (happybase) ──► HBase 明细与实时计数
HDFS ODS ──► Spark SQL 批处理 ──► DWD Parquet ──► ADS 聚合 ──► MySQL
DWD ──► Spark MLlib ──► 模型 (HDFS) + ads_predictions (MySQL)

                 ┌──────────────── 服务与展示层 ────────────────┐
MySQL / HBase REST ──► Spring Boot REST API ──► Vue3 + ECharts 大屏
```

采用**简化 Lambda 架构**：同一套 ODS/DWD/ADS 分层，批处理保证准确性与模型训练，流处理保证秒级监控。Spark 同时承担批与流，避免再引入 Flink 增加单机负担。

## 4. 数据设计

### 4.1 事件 JSON（Kafka / HDFS ODS）

```json
{
  "event_id": "2019-01-01|JFK|123|0800",
  "event_type": "flight_status",
  "event_time": "2026-10-27T10:15:00Z",
  "source_time": "2019-01-01T08:00:00Z",
  "flight": {
    "fl_date": "2019-01-01", "airline": "AA", "fl_number": 123,
    "origin": "JFK", "dest": "LAX", "crs_dep_time": "0800",
    "dep_delay": 15.0, "arr_delay": 10.0,
    "cancelled": 0, "diverted": 0, "distance": 2475
  }
}
```

- `event_time`：回放时**平移到当前墙钟时间**，保留事件间相对顺序，供水印/窗口使用。
- `source_time`：原始航班时间，供批处理与追溯使用。
- 回放速度：`--speedup 1440`（1 个历史日 = 1 个现实分钟）。演示时回放约 10 个历史日（约 8 万条），全量 300 万条用于批处理。

### 4.2 HDFS 目录

```
/flight/ods/raw/flights/          原始 CSV（bootstrap 上传）
/flight/ods/events/dt=YYYYMMDD/   Flume 写入的原始 JSON
/flight/ods/weather/dt=YYYYMMDD/  天气 JSON
/flight/dim/airline|airport/      Sqoop 导入的维度
/flight/dwd/flight/dt=YYYY-MM-DD/ 清洗后 Parquet
/flight/dwd/weather/hourly/       历史天气 Parquet
/flight/dws/                      聚合结果 Parquet
/flight/ml/model/<version>/       模型
/flight/checkpoint/realtime/      Streaming checkpoint
```

### 4.3 HBase 表

| 表 | RowKey | 列族 | 内容 |
|---|---|---|---|
| `flight_detail` | `fl_date|origin|fl_number|crs_dep_time` | `info` | airline, dest, dep_delay, arr_delay, cancelled, status, updated_at |
| `airport_realtime` | `origin|window_start` | `m` | departures, delayed, cancelled, avg_dep_delay, ontime_rate, visib, wind |
| `delay_alerts` | `origin|alert_ts` | `a` | level, reason, avg_delay, delayed_ratio |

写入方式：`hbase_sink.py` 消费 Kafka → happybase → HBase，批量 put（每 100 条或 2 秒 flush）。明细只保留回放事件，避免 300 万行全量入 HBase。

### 4.4 MySQL 表

**维度表**：`dim_airline`、`dim_airport`（含经纬度）、`dim_date`。

**ADS 结果表**：
`ads_realtime_kpi`（分钟级机场 KPI）、`ads_ontime_airline`、`ads_ontime_airport`、`ads_delay_cause`、`ads_route_stats`、`ads_delay_heatmap`、`ads_alerts`、`ads_predictions`、`ads_model_metrics`。

**设计要点**：所有 ADS 表带 `stat_time` 或 `stat_date` 主键/唯一索引，Spark JDBC 写入使用 `INSERT ... ON DUPLICATE KEY UPDATE`，保证任务重跑幂等。

### 4.5 Kafka Topic

- `flight-events`：3 分区，副本 1
- `weather-events`：1 分区，副本 1

## 5. 分层实现

### 5.1 采集层

**`collector/bootstrap_ods.py`**
- 将 Kaggle CSV 上传至 HDFS `/flight/ods/raw/flights/`（或转 JSON lines）。
- 解析机场坐标、生成 `dim_airport` / `dim_airline` / `dim_date` 并写入 MySQL。

**`collector/flight_replay.py`**
- 读取 CSV/Parquet，按 `CRS_DEP_TIME` 排序，逐条写 JSON 到 `/data/flight/logs/flight_events.log`。
- 时间平移：`event_time = now - (max_source_time - row_source_time) / speedup`。
- 维护 `.offset` 文件，重启从断点续放；支持 `--start-date/--end-date/--speedup/--loop`。

**`collector/weather_collector.py`**
- 每 5 分钟对 20 个主要机场调用 AWC：
  `https://aviationweather.gov/api/data/metar?ids=KJFK,KLAX,...&format=json&hours=1`
- 提取 `icaoId, obsTime, wspd, visib, flight_category, rawOb`，写 `/data/flight/logs/weather_events.log`。
- AWC 失败时降级 Open-Meteo；再失败则复用上一条并标记 `is_stale=1`。

**Flume `flume/flight-agent.conf`**
- Source：`taildir` 监控两个日志文件，`positionFile` 持久化偏移。
- Channel：memory channel（容量 10000，`keep-alive=3`）。
- Sink 1：Kafka sink → `flight-events` / `weather-events`（按拦截器或两个 agent 分流）。
- Sink 2：HDFS sink → `/flight/ods/events/%Y%m%d/%H`，设置 `rollInterval=60`、`rollSize=64MB`、`batchSize=1000`。
- 建议拆成 `flight-agent` 与 `weather-agent` 两个 agent，配置更简单。

**Sqoop**
- `sqoop import`：MySQL 维度表 → HDFS `/flight/dim/`，`--split-by` 指定主键，`-m 2`。
- `sqoop export`：将一个 ADS 结果表从 HDFS 导出到 MySQL，作为导出能力演示（其余表用 Spark JDBC 写入）。
- 兼容性处理：`ln -s $HADOOP_HOME/etc/hadoop $HADOOP_HOME/conf`；MySQL 驱动同时放入 `$SQOOP_HOME/lib` 与 `$HADOOP_HOME/share/hadoop/common/lib`；连接串加 `useUnicode=true&characterEncoding=utf8&autoReconnect=true`。

### 5.2 存储层

- HDFS 负责原始层与数仓层，DWD 统一 Parquet + Snappy，按 `dt` 分区。
- HBase 负责明细点查与实时计数，RowKey 前缀设计避免热点（origin 基数约 300，可接受）。
- MySQL 只存维度与聚合结果（每表万级以内），保证 API 查询毫秒级。
- 每周/每次演示后跑一次小文件合并：`spark-submit` 读取 ODS 当日分区写回 Parquet，或调小 Flume roll 频率。

### 5.3 处理层 — 实时

**`spark/streaming/realtime_kpi.py`**

1. `spark.readStream.format("kafka")` 读取 `flight-events`。
2. 解析 JSON，`withWatermark("event_time", "5 minutes")`。
3. 1 分钟滚动窗口，按 `origin` 聚合：
   - `departures = count(*)`
   - `delayed = sum(dep_delay >= 15)`
   - `cancelled = sum(cancelled = 1)`
   - `avg_dep_delay = avg(dep_delay)`
   - `ontime_rate = 1 - delayed / departures`
4. `foreachBatch`：
   - 从 MySQL 读取最新天气快照（20 行）广播关联，补充 `visib/wind/flight_category`。
   - JDBC 写入 `ads_realtime_kpi`（upsert）。
   - 同时写 HDFS `/flight/dws/realtime_kpi/` Parquet。
   - 告警判定：`avg_dep_delay > 30` 或 `delayed_ratio > 0.3` → 写 `ads_alerts`，Kafka 可选推送 `delay-alerts`。
5. Checkpoint：`/flight/checkpoint/realtime`；启动参数 `--driver-memory 3g --master local[4]`，触发间隔 10 秒。

**`spark/streaming/hbase_sink.py`**（独立 Python 进程）
- 消费 `flight-events`，解析后写 `flight_detail` 与 `airport_realtime`。
- 使用 happybase 连接 HBase Thrift 9090；批量 put；异常重试。
- 与 Spark 解耦，避免在 executor 中安装 HBase 依赖。

### 5.4 处理层 — 离线

**`spark/batch/clean_dwd.py`**
- 读 `/flight/ods/raw/flights/*.csv`。
- 类型转换、去空、过滤 `dep_delay/arr_delay` 异常值（如 |delay| > 1440）、去重（`fl_date+airline+fl_number+origin+crs_dep_time`）。
- 保留 `cancelled/diverted` 标记但单独处理。
- 关联 `dim_airline`、`dim_airport`。
- 写 `/flight/dwd/flight/dt=YYYY-MM-DD/` Parquet。

**`spark/batch/ads_stats.py`**
- 准点率：按航司、机场、月、星期、小时。
- 延误原因：`DELAY_DUE_*` 求和与占比（仅延误 ≥15 的航班）。
- 航线统计：`origin-dest` 航班量、平均延误、准点率，取 Top N。
- 热力图：星期 × 小时的平均延误与航班量。
- 机场拥堵特征：同一机场同一小时的计划航班数。
- 结果写 HDFS DWS + MySQL ADS（JDBC upsert）。

**性能要点**：广播维度表（`broadcast()`）、按 `fl_date` 分区裁剪、`spark.sql.adaptive.enabled=true`、输出前 `coalesce` 控制文件数。

### 5.5 MLlib 延误预测

**`spark/batch/train_model.py`**

- 数据：DWD Parquet；时间切分——2019–2022 训练/验证，2023 测试（避免随机切分泄漏）。
- 标签：`arr_delay >= 15` → `label=1`；回归任务可选 `arr_delay`。
- 特征（全部为起飞前可得）：
  - 类别：`airline, origin, dest, month, day_of_week`
  - 数值：`crs_dep_hour, distance, origin_hour_traffic`（机场小时计划航班数）
  - 天气：`origin_visib, origin_wind, dest_visib`（历史天气可获取时）
  - 目标编码：航司/机场历史延误率（**只用训练集计算**，防止泄漏）
- Pipeline：`StringIndexer → OneHotEncoder → VectorAssembler → StandardScaler`。
- 模型：LogisticRegression（基线）、RandomForest、GBTClassifier。
- 评估：`BinaryClassificationEvaluator`（AUC）、`MulticlassClassificationEvaluator`（F1/Accuracy）、混淆矩阵；`CrossValidator` 3 折；类别不平衡用 `weightCol` 或阈值调优。
- 目标：基线 AUC ≥ 0.65，加入天气/拥堵特征后 AUC ≥ 0.72。
- 输出：模型存 `/flight/ml/model/<version>/`；指标写 `ads_model_metrics`；对 2023 测试集打分写 `ads_predictions`（含 `predict_score, predict_label, model_version`）。
- 可解释性：RandomForest/GBT 的 `featureImportances` 映射回特征名，前端展示 Top 10。

**必须排除的泄漏字段**：`DEP_DELAY, ARR_DELAY, DEP_TIME, ARR_TIME, TAXI_OUT, TAXI_IN, WHEELS_OFF, WHEELS_ON, AIR_TIME, ELAPSED_TIME, DELAY_DUE_*`。

### 5.6 API 层（Spring Boot 2.7.18）

分层：`controller → service → repository(Spring Data JPA)`；统一响应 `{code, message, data}`；全局异常处理；`@CrossOrigin` 或网关放行；springdoc-openapi 提供 `/swagger-ui.html`。

| GET | `/api/airports/rank?limit=10` | MySQL | 机场准点率/延误排名 |
| GET | `/api/airlines/rank?limit=10` | MySQL | 航司排名 |

### 5.7 前端（Vue 3 + ECharts）

四个页面，Vue Router 管理：

1. **实时监控大屏 `Dashboard.vue`**
   - 顶部 KPI 卡片：当前准点率、延误航班数、平均延误、取消数。
   - 60 分钟趋势折线（准点率 + 航班量双轴）。
   - 美国机场地图：ECharts `geo` + `effectScatter`，点大小=航班量、颜色=延误率；需注册美国 GeoJSON（可从 `echarts/map/json/USA.json` 或公开 GeoJSON 获取），无地图时降级为经纬度散点。
   - 告警滚动列表；每 10 秒轮询。
2. **延误分析 `Analysis.vue`**
   - 航司/机场排名横向柱状图。
   - 五类延误原因堆叠柱状图/饼图。
   - 星期×小时热力图。
   - 航线网络 `lines` 图（Top 20 航线，带飞线动画）。
3. **预测与模型 `Prediction.vue`**
   - 模型指标卡片（AUC/Accuracy/F1）。
   - 混淆矩阵热力图、特征重要性条形图。
   - 高风险航班表格（按 `predict_score` 降序）。
4. **航班明细 `Flights.vue`**
   - 筛选：日期、航司、机场、延误区间。
   - 分页表格；点击行打开 Drawer，调用 `/api/flights/{rowkey}` 展示 HBase 明细。

工程要点：`vite.config.js` 配置 `/api` 代理到 `http://localhost:8080`；Axios 封装统一错误提示；轮询在 `onUnmounted` 清理；ECharts 实例在 `resize` 时重绘。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Sqoop 1.4.7 与 Hadoop 3.3 不兼容 | 采集层演示失败 | 统一 JDK 8；`etc/hadoop` 软链为 `conf`；驱动放两处；失败时用 Spark JDBC 兜底，但保留一次成功的 Sqoop 导入/导出 |
| 单机内存不足 | 服务 OOM、任务被杀 | 16GB 起步；Spark `local[2]`、HBase 堆 2GB、Kafka 堆 1GB；批/流分时运行；关闭不必要的 YARN |
| HBase 与 Kafka ZK 端口冲突 | 其中一个起不来 | Kafka ZK 改 2182，或 Kafka 用 KRaft 模式 |
| 回放事件时间与墙钟不一致 | 大屏“实时”体验差 | `event_time` 平移到墙钟，`source_time` 保留原值 |
| 天气 API 限流/不可用 | 实时天气缺失 | 5 分钟轮询、本地缓存上一份、Open-Meteo 降级、`is_stale` 标记 |
| 标签泄漏导致 AUC 虚高 | 答辩被质疑 | 严格排除事后字段；时间切分；目标编码只用训练集 |
| HBase 写入成为瓶颈 | 流处理反压 | 只写回放明细；批量 put；happybase 连接池；必要时采样 |
| Flume HDFS 小文件过多 | NameNode 压力 | 调大 `rollSize/rollInterval`；每日合并小文件 |
| Spring Boot 3 需要 Java 17 | 与 Sqoop 冲突 | 固定 Spring Boot 2.7.18 |
| 3M 样本被质疑“不够大数据” | 评分不利 | 提供 `--full` 模式切换到 3000 万行原始数据；强调管道与扩展性实验 |

## 13. 答辩口径建议

提前准备三个问题的回答：

1. **“数据是回放的，算实时吗？”**
   - 采集链路是真实运行的：回放器模拟数据源，Flume 真实采集，Kafka 真实传输，Spark Streaming 真实窗口计算。回放只是把历史时间轴压缩到演示时间，生产环境替换为真实数据源即可。

2. **“300 万行算大数据吗？”**
   - 单机伪分布式下 300 万行足以触发 Shuffle、分区、水印、Checkpoint 等分布式机制；同时提供 3000 万行全量模式与扩展性对比实验。

3. **“模型有没有作弊？”**
   - 展示排除字段清单、时间切分方式、目标编码只在训练集计算，以及混淆矩阵与基线对比。
